# 차단기 트립 관리 앱 개발 계획안

상태: 논의용 초안. 요구사항 기준은 [requirements.md](requirements.md)이며, 아래 추천 사항은 확정된 요구사항이나 기술 스택 변경을 의미하지 않는다.

사용자 확인: **한 기기에서 저장·조회**, **Android가 기본 출시 대상이며 iOS는 후속 확장 계획**. 현재 스택 유지안을 우선 추천하며 최종 설계는 논의 중이다.

## 1. 우선 판단

이 앱의 핵심은 현장에서 트립 이력을 정확히 입력하고, 같은 차단기의 이력과 교체 이후 트립 횟수를 빠르게 확인하는 것이다. 교체 후 0회부터 집계하고 이전 구간의 이력과 횟수를 별도로 보존하는 방식으로 확정했다.

사용자는 트립 횟수를 교체 판단에 활용하며, 같은 차단기가 하루에 두 번 트립하면 두 건으로 기록한다고 확정했다. 날짜가 같은 이력을 합치지 않고 발생 건수를 정확히 세는 것이 핵심 검증 대상이다.

확인된 조건에서는 **Kotlin + Jetpack Compose + Room**을 유지하는 안을 우선 추천한다. 안드로이드에서 등록·조회·수정·삭제·집계의 완성도를 확보하고, iOS 확장을 위해 업무 규칙과 저장소 접근을 화면에서 분리한다. iOS 출시 시점이 가깝거나 동시 개발로 바뀐다면 초기화 전에 Flutter와 Kotlin Multiplatform을 다시 비교한다.

## 2. 스택 비교

아래 적합도는 현재 요구사항을 기준으로 한 설계 판단이다.

| 후보 | 적합한 조건 | 비용 및 고려사항 | 현재 판단 |
| --- | --- | --- | --- |
| Kotlin + Jetpack Compose + Room | 안드로이드 우선 출시, 현장 입력, 로컬 저장 | iOS 확장 시 공통화와 플랫폼 구현 작업 필요 | 현재 우선 추천 |
| Flutter + Dart + Drift(SQLite) | Android·iPhone 공통 개발을 처음부터 진행 | Dart 도입, 검증 스크립트 변경, 양쪽 기기 검증 필요 | iOS 일정이 가까우면 초기 선택 후보 |
| Kotlin Multiplatform + Compose Multiplatform | Kotlin 기반으로 Android·iPhone 공통화 | 멀티플랫폼 빌드와 라이브러리 호환성 검토 필요 | Kotlin 유지 시 후속 확장 후보 |
| 웹/PWA + 서버 DB | PC에서 표 조회·관리, 설치 없이 여러 사용자가 접근 | 오프라인 저장·동기화·브라우저별 동작과 서버 운영 설계 필요 | PC 업무가 핵심이면 재검토 |

Flutter는 플랫폼 간 코드 공유를 지원한다. 그렇다고 각 플랫폼 검증이나 운영체제별 연동 작업이 없어지는 것은 아니다. [Flutter 공식 아키텍처](https://docs.flutter.dev/resources/architectural-overview)

Compose Multiplatform도 Android와 iOS에서 UI를 공유할 수 있다. 기존 Jetpack Compose 구성과 동일한 프로젝트 설정은 아니므로 멀티플랫폼 전환이 필요하다. 공통화 가능한 코드와 플랫폼 의존 코드를 구분해 두면 이후 전환 범위를 파악하기 쉽다. [Kotlin 공식 비교 문서](https://kotlinlang.org/docs/multiplatform/compose-multiplatform-and-jetpack-compose.html)

## 3. 1차 안드로이드 구성안

| 영역 | 제안 | 이유 |
| --- | --- | --- |
| 언어·UI | Kotlin + Jetpack Compose | 안드로이드 입력·조회 화면 구현 |
| 상태관리 | ViewModel + 불변 UiState + StateFlow | 검색·선택·입력·저장 상태 관리 |
| 데이터 | Room + SQLite + Flow, Repository로 접근 | 조건 조회·집계·트랜잭션·스키마 변경 관리 |
| 아키텍처 | 단일 app 모듈, presentation / domain / data 패키지 분리 | 작은 규모의 Clean Architecture + MVVM, 단순 전달용 UseCase 남발 방지 |
| 의존성 주입 | 생성자 주입 + 작은 수동 컨테이너 | 초기 구성 단순화와 테스트 대역 주입 |
| 버전 | 호환되는 안정 버전과 Gradle Wrapper 고정 | Kotlin·AGP·Gradle·JDK·라이브러리 호환성 확인 |
| 검증 | JUnit + 코루틴 테스트, Room 계측 테스트, Compose UI 테스트 | 업무 규칙·DB·안드로이드 사용자 흐름 검증 |

화면과 데이터 접근을 분리하고 복잡한 업무 규칙에만 UseCase를 둔다. 이는 UI·데이터 계층과 필요에 따른 도메인 계층을 제안하는 공식 권장사항을 작은 앱에 적용한 판단이다. [Android 아키텍처 권장사항](https://developer.android.com/topic/architecture/recommendations)

Room은 SQLite 접근과 마이그레이션을 지원하므로 정형화된 이력 저장과 조건 조회에 활용한다. [Room 공식 문서](https://developer.android.com/training/data-storage/room)

기존 AGENTS.md 및 Gradle 검증 진입점을 활용한다. iOS 확장은 별도 단계에서 공통 Kotlin 로직 추출, 저장소와 날짜 API의 호환성, Compose Multiplatform 또는 별도 iOS UI를 검토한다. 패키지를 나눴다는 이유만으로 iOS에서 바로 실행되는 것은 아니다.

초기에는 업무 규칙에 Android Context·리소스·UI 타입을 전달하지 않고, Repository 계약에 Room Entity를 노출하지 않는다. 날짜와 현재 시각 접근도 경계를 두어 후속 플랫폼 전환 시 교체 범위를 줄인다. Mac과 iOS 빌드 환경 확보는 후속 확장 단계에 포함한다.

## 4. 화면 구성 제안

교체 등록과 최초 입력의 상세 흐름은 [교체 등록 및 최초 구간 생성 설계안](replacement-flow.md)에 정리했다. 새로 제안한 화면·검증 정책은 검토 단계다.

기능 다섯 가지를 각각 독립 화면으로 만들기보다 검색과 입력 화면을 재사용한다. 아래 구성은 UI 확정 전 제안이다.

| 화면 / 동작 | 구성 | 연결되는 요구사항 |
| --- | --- | --- |
| 이력 조회 | 관·층·분전함번호·차단기명·트립일자 필터, 결과 목록 | 상세 조회, 수정·삭제 대상 검색 |
| 이력 상세 | 전체 8개 항목 표시, 수정 진입 | 상세 조회, 수정 |
| 등록 / 수정 폼 | 동일한 입력 컴포넌트 사용. 새 등록은 현재 교체 구간 기본 선택, 과거 트립은 이전 구간 선택. 수정은 기존 이력에 맞는 초기값 표시 | 등록, 수정 |
| 목록 선택 모드 | 단일·복수 선택, 삭제 건수 확인, 취소 | 삭제 |
| 횟수 조회 | 관·층·분전함번호·차단기명 필터, 교체 구간별 결과, 현재·과거 구간 구분 | 횟수 조회 |
| 교체 처리 (UI 제안) | 대상 차단기에 새 교체 구간을 시작하고 이전 구간 보존 | 교체 후 0회 시작; 화면·입력 항목은 미확정 |

휴대전화에서는 주요 식별 정보와 날짜를 목록에 보여주고 전체 항목은 상세 화면에서 확인하는 방식을 제안한다. 태블릿이나 PC에서 한눈에 비교하는 업무가 많다면 표 형태를 우선 설계한다.

입력 중 회전·백그라운드 전환, 저장 버튼 연속 클릭, 선택 후 데이터 변경도 함께 설계한다. 문자열 대문자 처리·공백 정리, 검색 기본값·결과 없음 안내, 정렬 규칙은 확정하여 requirements.md에 반영했다.

## 5. 데이터 설계에서 먼저 정할 부분

| 구분 | 제안 | 결정이 필요한 이유 |
| --- | --- | --- |
| 차단기 식별 | 관 + 층 + 분전함번호 + 차단기명 | 여러 트립 이력이 같은 차단기에 속하는 기준 |
| 트립 이력 식별 | 수정되지 않는 내부 ID, 원문 복합 Key 조합에 유일성 제약을 두지 않음 | 같은 입력값을 가진 별도 발생 건을 저장하고 개별 수정·삭제 |
| 동일 날짜 다회 트립 | 실제 발생마다 별도 이력으로 저장, 두 건은 2회로 집계 (확정) | 트립 횟수를 교체 판단에 활용하므로 날짜 기준 중복 제거 금지 |
| 날짜 저장 | 날짜 전용 값으로 모델링하고 YYYY-MM-DD 또는 일 단위 정수로 저장, 입력시각과 분리 | 시간대 변환으로 트립일자가 바뀌거나 입력 순서와 혼동되는 문제 방지 |
| 교체일 미상 | 최초 구간의 날짜 미상 허용 (확정). 저장은 nullable 교체일자 제안 | 날짜를 추정하지 않고 구간 ID로 트립 연결·집계, 화면에는 ‘교체일 미상’ 표시 |
| 교체일자 자동 표시 | 선택한 교체 구간의 교체일자 표시 (확정) | 새 트립은 현재 구간 기본 선택, 과거 트립은 이전 구간 선택 가능 |
| 횟수 집계 | 교체 구간별 집계, 새 구간은 0회부터 시작, 이전 구간 보존 (확정) | 교체 전후 횟수를 분리하여 교체 판단에 활용 |
| 장소 | 이력 당시 장소를 보존하는 방식 우선 검토 | 장소 수정이 과거 이력까지 바뀌는지 정의 필요 |

입력값이 같다는 이유로 신규 이력을 거절하거나 기존 행을 덮어쓰지 않는다. 트립 시간·회차 입력을 추가하지 않아도 내부 ID로 각각 구분할 수 있다. 실제 다회 트립과 동일 저장 요청의 재실행은 구분하여 설계한다. 검색 결과의 동일 항목 이력을 사용자가 구분할 표시 방식은 UI 설계 시 확정한다.

**차단기·교체 구간·트립 이력을 분리하는 모델로 확정했다.** 차단기 하나에 여러 교체 구간이 속하고, 각 트립은 한 구간에 연결한다. 구간별 트립 건수를 계산하고 트립이 없는 구간도 조회 결과에 포함한다. 새 교체 구간 생성 시 기존 트립을 삭제하거나 교체일자를 일괄 덮어쓰지 않는다.

교체 구간에도 내부 ID를 두고 교체일자는 속성으로 관리한다. 새 트립은 현재 구간을 기본 선택하고, 과거 트립은 이전 구간을 선택하여 저장한다. 교체 당일에도 선택 구간에 연결하여 전후 이력을 분리한다. 날짜 불일치 시 저장 제한과 교체 기록 정정·삭제 규칙은 확정했으며, 최초 구간 생성 화면은 설계안에 정리했다.

## 6. 단일 기기와 공유 사용의 차이

| 항목 | 단일 기기 | 여러 기기 공유 |
| --- | --- | --- |
| 저장 | Room + SQLite | 서버의 공유 데이터 + 필요에 따라 로컬 캐시 |
| 사용자 구분 | 요구가 없으면 로그인 생략 | 사용자 식별, 조회·수정·삭제 권한 정의 |
| 오프라인 | 기기 내 CRUD 가능 | 오프라인 조회만 허용할지 수정도 허용할지 결정 |
| 충돌 | 한 기기 내부 중복과 수정 검증 | 동시 수정, 중복 등록, 삭제 전파 정책 추가 |
| 운영 | 데이터 이전·백업 방법 논의 | 서버 운영·백업·접근 관리 추가 |

현재 선택은 단일 기기 사용이다. 서버·계정·동기화는 초기 범위에서 제외하는 안으로 계획한다. 향후 공유 기능을 추가할 경우에는 동기화 큐와 충돌 처리까지 별도로 설계해야 한다. [Android 오프라인 우선 앱 설계](https://developer.android.com/topic/architecture/data-layer/offline-first)

백업·복원, CSV/Excel 내보내기, 계정, 변경 이력은 원문 범위 밖이다. 현장 운영에 필요한지 논의하여 별도 범위로 확정한다.

## 7. 구현 순서와 완료 기준

실행 단위로 나눈 작업은 [구현 작업 목록](implementation-plan.md), 테이블·제약·조회·트랜잭션은 [DB 상세 설계](data-model.md)를 따른다.

| 단계 | 작업 | 완료 기준 |
| --- | --- | --- |
| 1. 운영 조건 확정 | 단일 기기·Android 우선 확인 완료, 최소 지원 OS·배포 방식 결정 | 안드로이드 개발·검증 경로 확보 |
| 2. 업무 규칙 확정 | 다회 등록·교체별 집계·구간 선택 확인 완료, 교체 입력·날짜 검증·필수값·검색 방식 정리 | requirements.md와 test-plan.md에 예시 포함 |
| 3. 기반 구성 | 안드로이드 앱 생성, 버전 고정, SDK/JDK, DB 스키마, 테스트 러너 | Android 빈 앱 실행 및 Lint·테스트 확인 |
| 4. 등록 → 상세 조회 | 검증 규칙·저장·폼·검색을 작은 단위로 연결 | 등록한 이력이 재실행 후에도 조회됨 |
| 5. 수정·삭제 | 공통 폼, ID별 대상 식별, 다중 선택·확인·트랜잭션 | 입력값이 같아도 대상만 수정·삭제되고 취소 시 보존됨 |
| 6. 교체 처리·횟수 조회 | 새 교체 구간 생성과 구간별 집계 구현 | 교체 직후 0회, 과거 구간 보존, 같은 날 다회 트립 및 수정·삭제 결과 검증 |
| 7. 현장 검증·배포 | Android 실제 기기 입력, 날짜 선택, 오류 안내, 설치·업데이트 확인 | 업무 시나리오 완료 및 업데이트 시 데이터 보존 |
| 후속. iOS 확장 | 일정 확정 후 공통화 범위·UI·Mac 환경·배포 방식 결정 | iPhone에서 동일 업무 규칙과 실제 기기 흐름 검증 |

각 기능은 규칙 테스트 → 구현 → 해당 DB/UI 검증 순서로 진행한다. 화면만 먼저 모두 만든 뒤 저장을 붙이기보다 등록부터 조회까지 연결된 흐름을 먼저 완성한다. 공유 사용이 선택되면 3단계 이전에 서버·인증·동기화 설계 단계를 추가한다.

## 8. 다음 결정

검색 조건·필수값·정렬·장소 표시는 확정했으며 requirements.md와 테스트 계획에 반영했다. 상세 규칙과 예시는 [검색·입력·정렬 설계](search-input-design.md)에 정리했다.

운영 조건은 **한 기기에서 저장·조회, Android 우선 출시, iOS 후속 확장**으로 확인했다. 다음으로 데이터 모델과 집계 결과에 영향을 주는 업무 규칙을 아래 예시로 확정한다.

1. 교체 등록은 차단기를 선택해 ‘교체 등록’에서 날짜를 입력하는 흐름으로 할 것인가?
2. 최초 교체 구간을 첫 트립과 함께 생성·저장하는 화면 흐름으로 할 것인가?

교체일 정정·구간 삭제·날짜 검증 규칙은 확정했고 [교체 설계안](replacement-flow.md#7-교체일-정정-화면-제안)과 requirements.md에 반영했다. 날짜 정정 시 횟수 유지, 트립이 있는 구간 삭제 제한, 빈 현재 구간 삭제 시 직전 구간 복원, 날짜 모순 시 저장 제한을 적용한다.

답변에 따라 계획안을 확정하고 요구사항·기술 지침을 함께 갱신한다.
