# 구현 작업 목록

기준 문서는 [requirements.md](requirements.md), DB 기술 설계는 [data-model.md](data-model.md)다. 앱 기반 구성, 입력 규칙 일부, Room 저장·조회 계층을 구현했다. 전체 업무 기능은 아직 구현하지 않았다.

현재 상태: 최초/기존 트립 등록·상세 검색·상세 보기·횟수 조회에 이어, 트립 한 건 수정과 확인 후 단일·복수 삭제를 구현했다. 0.2.0 APK는 사용자 확인을 받았으며 0.4.0에서 관·층별 분전함 현황, 차단기 펼치기/상세 진입, 명시적 선택 모드와 미니멀 디자인을 추가했다. 새 UI와 수정·삭제 기능은 실제 기기 확인이 필요하다. 최신 자동 검증 결과는 [검증 계획](test-plan.md)의 실행 현황을 따른다. 남은 업무 기능은 새 교체 등록 및 교체 구간 날짜 정정·삭제다.

## 1. 작업 순서

| 순서 | 작업 단위 | 산출물 | 완료 조건 |
| --- | --- | --- | --- |
| 1 | 안드로이드 기반 구성 | 앱 모듈, Compose, Room, 버전 카탈로그, Gradle Wrapper, 테스트 실행 환경 | 빈 앱 실행·단위 테스트·Lint·Debug APK 빌드 |
| 2 | 업무 값·검증 | 차단기 식별값, 층 정렬, 날짜 경계, 미상 날짜, 문자열 정규화 | JVM 규칙 테스트 통과 |
| 3 | Room 저장소 | 3개 업무 테이블, DAO, Repository, 스키마 내보내기 | FK·다회 트립·구간 집계·롤백 테스트 통과 |
| 4 | 최초 등록과 상세 조회 | 공통 입력 폼, 검색 목록, 상세 화면 | 첫 등록 → 앱 재실행 → 동일 이력 조회 |
| 5 | 기존·과거 트립 입력 | 현재 기본 선택·이전 구간 선택 | 과거 트립 등록 시 현재 횟수 유지 |
| 6 | 교체 등록과 횟수 조회 | 교체 폼, 구간 필터, 횟수 정렬 | 이전 구간 보존·새 구간 0회·대표 장소 정확성 |
| 7 | 수정·삭제 | 트립 수정·복수 삭제, 교체일 정정·빈 구간 삭제 | 한 건 수정 범위·날짜 오류·현재 구간 복원 검증 |
| 8 | 실제 기기 마무리 | 입력 복원, 키보드·날짜 선택, 오류 안내, 업데이트 확인 | 주요 업무 흐름과 데이터 보존 확인 |

각 작업은 해당 규칙의 실패하는 테스트 확인 → 최소 구현 → 검증 순서로 진행한다. 테스트 ID는 [test-plan.md](test-plan.md)와 상세 설계의 시나리오를 사용한다.

## 2. 코드 배치

```text
app/src/main/.../
  domain/                 # 업무 값·검증·Repository 계약
  data/local/             # Room Entity·DAO·DB·날짜 변환
  data/repository/        # 트랜잭션 및 도메인 모델 변환
  presentation/trips/     # 이력 검색·상세·등록·수정
  presentation/periods/   # 교체·구간 선택·정정
  presentation/counts/    # 구간별 횟수 조회
  presentation/common/    # 재사용 입력·선택 컴포넌트
  di/                     # 수동 의존성 조립
app/src/test/.../          # 업무 규칙·ViewModel 테스트
app/src/androidTest/.../   # Room·Compose 기기 테스트
```

도메인 모델은 Android Context나 Room Entity를 참조하지 않는다. 단순 DAO 호출마다 UseCase를 만들지 않고 복잡한 검증·저장 절차만 분리한다.

## 3. 첫 구현 범위

첫 구현의 목표는 ‘한 건 등록하고 앱을 다시 열어 조회할 수 있는 상태’다. 기반 구성과 문자열·날짜 검증, DB 저장·검색을 먼저 연결한다. 교체 정정이나 복수 삭제는 후속 작업으로 이어간다.

앱 이름은 `Trip Tracker`, applicationId `com.triptracker.app`, 최소 Android 8.0(API 26)이다. 배포 전 식별자와 지원 기기 범위를 최종 확인한다. 프로젝트 로컬 JDK·SDK는 doctor 스크립트로 점검한다.

## 4. 남은 사용자 흐름 검토

최초 구간을 첫 트립과 함께 저장하는 흐름은 확정·구현했다. 횟수 조회에서 차단기를 선택해 새 교체를 등록하는 화면은 [화면 설계](replacement-flow.md)의 후속 검토 대상이다.

검색·집계·날짜 검증·미상 날짜·수정 삭제의 확정 규칙을 다시 승인받는 단계는 두지 않는다. 자동 교체 권고 임계값은 현재 구현 범위에 포함하지 않는다.
