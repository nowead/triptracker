# 요구사항 검증 계획

기준 문서는 requirements.md다. 전체 표는 기능별 검증 계획이다. 현재 구현한 테스트와 나머지 미구현 테스트를 아래 실행 현황으로 구분한다.

## 실행 현황

0.4.0 최종 검증: 로컬 테스트 56개 통과, Lint 오류 0건, Debug APK 빌드 성공. 분전함 현황과 미니멀 디자인·선택 모드를 적용하고 기기 테스트 APK도 생성했다. 연결 기기 부재로 계측 실행은 미검증이다.

- `app/src/test/java/com/triptracker/app/domain/InputRulesTest.kt`: JUnit 11개 통과. 관·층 선택, 영문 정규화·한글 보존, 필수 문자열, 현지 오늘 날짜, 미상·교체 경계·미래 날짜를 검증한다. REG-01~03 및 INPUT-01~02의 규칙 부분을 다루며 UI 전체 완료를 뜻하지 않는다.
- 실제 기기 수동 확인(2026-09-15, 사용자 보고): Debug APK 설치·실행 성공, 시작 화면에 ‘트립트래커’ 표시 확인. 등록·조회 등 업무 기능 검증은 포함하지 않는다.
- `app/src/androidTest/java/com/triptracker/app/AppLaunchTest.kt`: 시작 화면 테스트 작성·컴파일 완료. 자동 계측 테스트는 아직 실행하지 않았다.
- `app/src/test/java/com/triptracker/app/data/TripRepositoryTest.kt`: Robolectric / API 28의 실제 Room 저장소 테스트 29개. 기존 저장·검색·집계·영속성 22개에 선택한 동일값 이력만 수정, ID/등록시각 유지, 구간 이동 시 양쪽 집계, 새 대상 차단기 생성, 날짜·삭제된 대상 거절, 수정 실패 시 신규 대상 롤백, 선택 ID만 삭제·0회 구간 유지, 복수 삭제 실패 시 전체 롤백을 추가했다.
- `TripViewModelTest.kt`: 13개. 관·층·분전함별 합계/0회 보존, 검색과 독립된 현황 갱신, R1/R10 정확 구분, 명시적 선택 모드 검증을 추가했다. 기존 입력·검색 검증과 함께 수정 진입 시 원래 과거 구간 선택, 수정 후 검색 조건 유지, 수정 취소, 삭제 확인·취소, 재조회 시 선택 해제, 삭제 실패 시 선택 유지, 연속 확인 중복 처리 방지를 검증한다.
- `RegistrationScreenTest.kt`: 3개. 새 현황의 앱 이름·관 필터·분전함 펼치기/접기·차단기 진입·선택 삭제 후 현황 갱신을 추가 검증한다. 실제 Compose 폼의 최초/반복 등록 1→2회 흐름과 선택한 이력만 수정 → 복수 삭제 취소/확정 → 단일 삭제 → 0회 구간 표시를 검증한다. Robolectric 테스트이며 실제 기기 확인과는 구분한다. 로컬 테스트 합계 56개.
- `app/src/androidTest/java/com/triptracker/app/TripDatabaseDeviceTest.kt`: 같은 날 두 건 저장 후 재연결 보존, 한 건 수정 시 등록시각·다른 이력 보존, 복수 삭제 후 재연결 시 0회 구간 유지 검증을 작성·컴파일했다. `bash scripts/build_and_test.sh --device`는 연결 기기 없음으로 실패하여 자동 계측 테스트는 미실행이다.
- `bash scripts/build_and_test.sh`: 로컬 테스트·Lint·Debug APK를 검증한다. 등록·검색·상세·횟수와 트립 수정·삭제를 구현했으며 새 교체 등록·교체 구간 정정/삭제는 후속 작업이다.

## 구현 전에 확정할 사항

| 항목 | 영향 |
| --- | --- |
| 새 교체 입력 화면 구성 | 교체 처리 UI 테스트, COUNT-03 |

미확정 항목에 의존하는 테스트와 기능은 기준 확정 후 작성한다. 독립적인 개발 도구 설정은 계속 진행할 수 있다.

검색·필수값·정렬·장소 표시의 상세 시나리오는 [검색·입력·정렬 설계](search-input-design.md#5-검증-시나리오)에 정리했다. 현재 구현한 검증 범위는 위 실행 현황을 따른다. SEARCH-05의 재조회 시 삭제 선택 해제도 ViewModel 테스트에 포함했다.

최초 생성의 INIT-01~04와 트립 저장 요청 중복 방지를 검증했다. 실제 교체 등록의 REPLACE 시나리오는 후속 구현 대상이다. [상세 시나리오](replacement-flow.md#6-검증-시나리오)를 참고한다.

교체일 정정·구간 삭제·트립 연결 변경은 [수정·삭제 추가 검증 계획](replacement-flow.md#10-수정삭제-추가-검증-계획)의 PERIOD-01~09로 구체화했다. 확정된 업무 정책에 대한 검증 계획이며 테스트 코드는 아직 작성하지 않았다. 미래 날짜 거절, 교체 경계일 허용, 미상 날짜의 알려진 경계 검증도 포함한다.
